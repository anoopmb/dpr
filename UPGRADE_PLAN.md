# DPR System Upgrade Plan

**Source:** `kalady malayattor DPR.xlsx` — CRF (Calamity Relief Fund) road + drainage project,
Kalady–Malayattoor, September 2023 – July 2024.

**Method:** Every sheet was read in full. All gaps are derived directly from observed data.
No assumptions have been made.

---

## What the Excel contains (complete inventory)

### 13 sheets total

| Sheet | Content |
|---|---|
| `DPR - Sept+October` through `DPR - July` (10 sheets) | Monthly production + expenditure registers |
| `DPR - irish upto 29` | Sub-register for Irish drain work only |
| `Detailed measurements` | Measurement Book — 1,217 rows of chainage-based dimension calculations |
| `Sheet1` | Mini-MB for specific culvert locations across 4 chainages |

### Structure of each monthly DPR sheet

**Section A — Daily Production Register** (BOQ items × days):
- Rows: every BOQ item from the contract
- Columns: one pair (Quantity, Amount) per calendar day of the month
- Fixed columns: Item No, Description, Unit, Rate, Agreed Quantity, Up to Date Quantity, Up to Date Amount
- Section sub-totals: one row per section (Road Works, Drainage Works, Traffic Safety)

**Section B — Expenditure** (client enters costs here; user confirmed separate screens cover this):
- B.1 Material Consumption — material name, unit, rate, daily qty + amount
- B.2 Machinery — machine name, unit (Daily/Hr), rate, daily qty + amount
- B.3 Labour — category name, unit (Nos), daily rate, daily head count + amount
- B.4 (numbered "5)") Plant Expense — plant cost items, daily qty + amount
- B.5 (numbered "4)") Miscellaneous Expenses — FOOD, PURCHASE, Fuel, Other Dept — daily amount only (no qty × rate)

**Section C — Weekly P&L Summary**:
- Columns: each day + weekly sub-total columns
- Rows: Total Income (= production value for that period) | Total Expense (sum of B.1–B.5) | Net Profit/Loss | Profit/Loss %
- Cumulative snapshots: "Total from 21-09-23 to {date}" columns

## Zero-production day scenario — analysis (confirmed from data)

**User's question:** On some days the contractor has no BOQ quantity to enter (pre-work, mobilization, preparatory work) but still incurs real expenditure. Is this expected, and how should the system handle it?

**Confirmed: yes, this is normal and well-documented in the client's data.**

There are two distinct scenarios where income is low or zero, and both are legitimate:

---

### Scenario A — Preparatory days (zero production, non-zero expense)

The contractor is doing work that is a *prerequisite* for a BOQ item, but the BOQ item itself cannot be measured or recorded until the work is physically complete. For example:
- Tying rebar and setting formwork for an RCC pour — the BOQ item "RCC M20 Raft" can only be entered after concrete is poured and cured
- Dewatering and site preparation before earthwork begins
- Mobilizing machinery to site, setting up camp

**During these days:** Income = 0 (no BOQ qty can honestly be entered). Expense = real costs (JCB, labour, food, fuel).

**Evidence from July DPR (rows 155–158):**
```
Day         Income    Expense     P&L %
July 1        0       44,100      -100%
July 2        0       33,880      -100%
July 3        0       12,370      -100%
July 4        0       40,830      -100%
July 5        0       28,490      -100%
July 6        0       30,180      -100%
July 7   52,567,099  ...          +ve (big BOQ measurement entered after completion)
```

**Evidence from Sept+Oct DPR (rows 134–138):**
```
21-Sep   2,710   16,435   -83.5%   (Earthwork & Clearing grass)
22-Sep   1,600   16,010   -90%     (Earthwork & Clearing grass)
26-Sep   1,050   13,180   -92%     (Earthwork & Clearing grass)
27-Sep   1,800   16,375   -89%     (Earthwork & Clearing grass)
```
On earthwork clearing days: very small income (clearing grass BOQ item at ₹50,000/Hec — small qty per day) but mobilization costs are heavy.

**In Excel:** On days where Income = 0, the Profit/Loss % column shows `#DIV/0!` (Excel's divide-by-zero error). This is a known issue in the client's own spreadsheet — the system must NOT replicate this error.

---

### Scenario B — Negative quantity corrections

Item 2.002 Dismantling: Up to Date Qty = −199 Cum (previously over-counted, now corrected).
Item 2.016 Back filling: Up to Date Qty = −108.24 Cum.

This is an explicit re-measurement correction, not a preparatory day. The contractor over-entered a quantity in a previous day and is correcting it by entering a negative qty on a later day.

**This is GAP 6 (renamed 6b below).**

---

### Design implications for the system

| Scenario | Income | Expense | P&L Result | System must... |
|---|---|---|---|---|
| A: Pre-work day | 0 | > 0 | Negative (= -expense) | Accept without error. P&L% shows "—" |
| B: Neg qty correction | May be negative | Normal | May be negative | Accept negative qty in production entries |
| Normal day, heavy cost | > 0, small | > 0, large | Negative % | Display informatively, not as alert |
| No-work day | 0 | 0 | 0 | GAP 11 — separate "no work" flag |

**Key rules derived from this analysis (must be implemented, not shortcuts):**

1. A DPR header with zero production entries but non-zero expenses is **valid**. Do not validate that at least one production qty > 0.
2. `profit_percent` must return `null` (not divide-by-zero error) when `production_value = 0`. UI must show "—" or "N/A", not a crash or a zero.
3. Negative P&L must be **informational** — displayed as a number (possibly red), not as an error state or a validation block.
4. Weekly/monthly cumulative P&L is the meaningful view for management decisions. Individual daily P&L is highly volatile, especially early in the project. The UI should emphasize period aggregates over daily snapshots.
5. "Income" in the P&L context = production value (BOQ qty × rate). It is NOT payments received from client. These are different numbers on different screens.

## Gap analysis — what is NOT covered

### GAP 1 — BOQ has no section/category grouping (CRITICAL)

**Observed:** Items are grouped into numbered sections: "1. ROAD WORKS", "2. DRAINAGE WORKS", "3. Traffic Safety Appurtenances". Item numbers like `1.005`, `2.009` are part of the official contract document and appear on government payment certificates.

**Current state:** `BoqItem` has no parent grouping. Item numbers are not stored.

**Required backend change:**
- New table `boq_sections`: `id`, `project_id` (FK), `section_no` (e.g. "1", "2", "3"), `section_name` (e.g. "ROAD WORKS"), `sort_order`
- `boq_items` table: add `section_id` (FK → boq_sections, nullable for backward compat), `item_no` varchar(20) (e.g. "1.005")
- Alembic migration required

**Required API change:**
- `GET /boq/{project_id}` should return sections with nested items
- `POST /boq/sections` — create section
- `PATCH /boq/sections/{id}` — rename/reorder
- `DELETE /boq/sections/{id}` — only if no items
- `BoqItemCreate` / `BoqItemRead` schemas add `section_id`, `item_no`

**Required UI change:**
- BOQ page: section header rows between BOQ items (like a grouped table)
- "Add Section" button before adding items
- Item number field in BOQ item form
- Section sub-total row at bottom of each group

### GAP 2 — Daily Production Entry in DPR (CRITICAL)

**Observed:** The primary function of the DPR is a daily production register. For each calendar day, the supervisor enters the quantity of each BOQ item executed that day. Amount = qty × BOQ rate (auto-computed). This is the document that proves work was done and goes to the client/government.

**Current state:** Our DPR captures site diary entries (issues, photos, materials consumed, machinery hours). It does NOT capture daily production quantities against BOQ items. These are entirely different things.

**Required backend change:**
- New table `dpr_production_entries`:
  - `id` UUID PK
  - `dpr_header_id` UUID FK → `dpr_headers`
  - `boq_item_id` UUID FK → `boq_items`
  - `qty_today` NUMERIC(14,3) — quantity executed on this date; **negative values are allowed** (correction entries — see GAP 6b; pre-work zero-production days — see Zero-production day analysis)
  - `amount_today` NUMERIC(14,2) — computed: qty_today × boq_item.rate, stored not computed (same pattern as billing); will be negative when qty_today is negative
  - `chainage` VARCHAR(100) nullable — location range e.g. "2/130–2/390"
  - `remarks` TEXT nullable
  - UNIQUE (dpr_header_id, boq_item_id) — one entry per item per day
  - Alembic migration required
- `dpr_headers` table: add `daily_work_summary` VARCHAR(500) nullable — free-text description of the day's activity type (e.g. "Earthwork and Clearing grass", "Concreting and steel work"); matches the activity notes row observed in client's spreadsheet
- `DprHeaderCreate` / `DprHeaderRead` schemas: add `daily_work_summary: str | None`
- **Zero-production validity rule:** A DPR header with zero production entries and non-zero expenses is valid. This covers pre-work days (mobilization, formwork setting, steel tying, site prep) where real costs are incurred but no BOQ qty can be claimed until the corresponding BOQ work is physically complete and measurable. Do NOT add any validation that requires at least one production entry with qty > 0.

- New service: `DprProductionService`
  - `upsert_entry(dpr_header_id, boq_item_id, qty, chainage, remarks)` — creates or updates; computes amount = qty × rate from boq_item; does not validate qty > 0 (both zero and negative are valid)
  - `list_for_header(dpr_header_id)` — all entries for a day
  - `cumulative_for_project(project_id, up_to_date)` — sum qty and amount per boq_item across all dpr_headers up to a date

**Required API change:**
- `PUT /dpr/{header_id}/production/{boq_item_id}` — upsert production entry for one BOQ item
- `GET /dpr/{header_id}/production` — list all entries for a DPR header
- `GET /projects/{project_id}/production-progress` — cumulative totals per BOQ item

**Required UI change:**
- `DprTodayPage`: add a "Production" tab alongside existing "Issues / Materials / Machinery" tabs
- Add "Today's activity" text input at the top of the DPR form (maps to `daily_work_summary`, optional)
- Production tab: table listing all BOQ items for the project (grouped by section)
  - Each row: Item No, Description, Unit, Rate, Today's Qty (editable input), Today's Amount (auto-displayed = qty × rate)
  - Chainage input per row (optional)
  - "Save" saves all entered quantities at once (bulk upsert)
  - Rows with qty = 0 or blank are not saved (clean state)
  - **Leaving all rows blank is valid** — the DPR header still saves as a pre-work day with expenses only
- New desktop page: `ProductionProgressPage` — table showing for each BOQ item:
  - Agreed Qty | Executed to Date | Amount to Date | Remaining Qty | % Complete
  - Grouped by section with section sub-totals
  - Date filter to see "up to date" as of any past date

**Observed:** Every entry in the Detailed Measurements sheet has a Chainage column: `2/130–2/390`, `3/686–3/799`, `5/500 & 1/800`, etc. This is the road kilometer range where the work was measured. Without it, measurements cannot be verified by the department.

**Current state:** `Measurement` model has no location/chainage field.

**Required backend change:**

- `MeasurementCreate` / `MeasurementUpdate` / `MeasurementRead` schemas: add `chainage: str | None`
- Alembic migration required

**Required UI change:**
- Measurement form (desktop `MeasurementsPage` + field `MeasurementEntryPage`): add optional "Chainage / Location" text field
- Measurement list table: add Chainage column

### GAP 4 — "Up to Date" BOQ progress view (CRITICAL)

**Observed:** Every DPR sheet shows for each BOQ item: Agreed Quantity, Up to Date Quantity (cumulative from project start), Up to Date Amount (cumulative from project start). This is the fundamental progress tracking view used to prepare running bills and progress reports.

**Current state:** No such view exists. Billing is based on locked measurements, not on daily production entries. After GAP 2 is implemented, this view is a query against `dpr_production_entries`.

**Required API change:**
- `GET /projects/{project_id}/production-progress?as_of={date}` (already listed under GAP 2, same endpoint)
- Response per BOQ item: `{ boq_item_id, item_no, description, unit, rate, agreed_qty, executed_qty, executed_amount, remaining_qty, percent_complete }`
- Grouped by section in response

**Required UI change:**
- New desktop page `ProductionProgressPage` (accessible from sidebar for PM/QS/Admin):
  - Section-grouped table with the fields above
  - "As of date" date picker defaulting to today
  - Section sub-total rows
  - Grand total row
- Link from DPR header to this view

### GAP 5 — Measurement Book: multiple work elements under one date (IMPORTANT)

**Observed in Detailed Measurements sheet:** A single date has multiple work type entries. e.g., 2023-10-03 has: M20 Drain-side wall, M20 Slab, M20 Raft, M15 PCC Bed, Steel 10mm, Steel 8mm — each with their own No/L/B/H/Qty set. Within one work type, there are multiple sub-dimension lines (e.g. steel calculations show multiple bar sizes).

**Current state:** Our Measurement model supports one set of dimensions per entry. The field UI creates one entry at a time. Multiple measurements on the same day are created as separate entries, which is functionally correct but the MB display does not group them by date in a compact way.

**Also observed in Sheet1:** A mini-MB table where 4 different chainages are laid out as side-by-side column groups on the same rows. Each column group has the same work items but different No/L/B/H values for that chainage.

**Required change:**
- No schema change needed — separate entries per work element is the right approach
- UI change: in `MeasurementsPage`, add grouping by date in the table so all measurements for the same date are visually grouped together
- In field `MeasurementEntryPage`: after saving one entry, offer "Add another measurement for today" without navigating away (current flow navigates back)
- The multi-chainage parallel layout (Sheet1 pattern) is a print/report concern, not a data entry concern — not needed in the web UI

### GAP 6a — Zero-income pre-work days (IMPORTANT)

**Observed:** See "Zero-production day scenario — analysis" section above. July DPR shows 6 consecutive days with Income = 0, Expense = ₹12,000–₹44,000 each day. Sept+Oct DPR shows the first weeks with very small income (₹1,050–₹2,710) and large expense (₹13,000–₹16,000), resulting in P&L of −83% to −92%.

These are normal construction pre-work / mobilization days. The contractor has real expenditure but cannot enter BOQ production quantities until the corresponding item is physically complete and measurable.

**Current state:** Zero-production DPR headers are not explicitly handled — GAP 2 must be implemented in a way that does not require a production entry.

**Required change:**
- Already incorporated into GAP 2: `dpr_production_entries` table has no NOT NULL constraint on qty count; zero entries for a day is valid
- `DprProductionService.upsert_entry` must accept qty = 0 (though it won't be stored if the row has qty = 0 — caller skips saving blank rows)
- No new DB changes beyond what GAP 2 already specifies
- The profitability endpoint (GAP 8) must handle `production_value = 0` without a divide-by-zero in `profit_percent`

### GAP 6b — Negative quantity corrections in BOQ items (IMPORTANT)

**Observed:** Item 2.002 Dismantling shows Up to Date Qty = −199 Cum and Up to Date Amount = −₹1,39,300. Item 2.016 Back filling shows Up to Date Qty = −108.24. These are quantity corrections — the contractor previously over-counted a quantity and is correcting it by entering a negative qty on a later day.

**This is a different scenario from GAP 6a.** Zero-income pre-work days have zero entries. Negative-qty corrections have an explicit negative number in `qty_today` to cancel out a prior entry.

**Current state:** `dpr_production_entries.qty_today` will be NUMERIC(14,3) — PostgreSQL allows negative by default. But `MeasurementService.validate_measurement_against_boq` rejects quantities that exceed the agreed qty. If cumulative goes negative, the system may reject further entries.

**Required change:**
- `dpr_production_entries`: explicitly allow negative qty_today (correction entries) — already captured in GAP 2 schema spec
- Do not validate `qty_today > 0` at entry level — allow negative as a correction
- BOQ progress view: show negative cumulative quantity as a visual warning (amber/orange flag) but do not block it — it is a valid business state
- `MeasurementService.validate_measurement_against_boq` should check against cumulative from `dpr_production_entries` only after GAP 2 is implemented; for now, the measurement tolerance check already handles this via `default_measurement_tolerance_percent`
- No DB schema change needed beyond GAP 2 — just ensure no CHECK CONSTRAINT `qty_today > 0` is added anywhere

### GAP 7 — Supervisor name recorded on DPR header (MODERATE)

**Observed:** Every DPR sheet header shows "Name of Supervisor: Aneesh" or "Dheeraj/Arun". The DPR is a formal document attributed to a named supervisor. Over the project lifetime, two different supervisors were responsible for different months.

**Current state:** `DprHeader` has `submitted_by` (UUID FK → users). The user's full name is available but the DPR header does not record a display supervisor name for cases where the entering user and the responsible supervisor differ.

**Required backend change:**
- `dpr_headers` table: add `supervisor_name` VARCHAR(200) nullable
  - Default: populated from the submitting user's `full_name` at submit time
  - Can be overridden (e.g., site engineer enters on behalf of supervisor)
- `DprHeaderRead` / `DprHeaderCreate` schemas: add `supervisor_name`
- Alembic migration required

**Required UI change:**
- DPR today page: show supervisor name field (pre-filled from logged-in user, editable)
- DPR list / history view: show supervisor name column

### GAP 8 — Weekly P&L summary (production income vs expenditure) (MODERATE)

**Observed in Section C of every monthly sheet:** The client computes weekly running totals:
- Total Income = sum of (BOQ qty × rate) for all production entries in the period — this is the **value of work done**, NOT payments received from client. A project can have negative P&L while having positive cashflow (and vice versa).
- Total Expense = sum of material + machinery + labour + plant + misc costs for the period
- Net Profit/Loss = Income − Expense
- Profit/Loss % = Net P&L / Income × 100

**Confirmed from data:** Negative P&L is the norm in the early weeks of this project (mobilization, earthwork, pre-work). From Sept 21–27: every single day had negative P&L except Sept 25. In July: 6 consecutive zero-income days with ₹30,000–₹44,000 daily expense each. This is a normal contractor cash-flow pattern — high early costs, with BOQ measurement income "catching up" once work items are physically complete and measurable.

**The Excel spreadsheet shows `#DIV/0!`** in the Profit/Loss % column on all days where Total Income = 0. This is the client's own tool's limitation. Our system must handle this correctly.

**Current state:** Our Dashboard shows billing totals (running bills raised) vs payments received. That measures cashflow. The client's P&L measures work-value vs cost — a different thing.

**Required backend change:**
- New API endpoint `GET /projects/{project_id}/profitability?from_date={date}&to_date={date}`:
  - `production_value`: sum of dpr_production_entries.amount_today in date range (can be 0 or negative)
  - `material_cost`: sum of expenses where category = material in date range
  - `machinery_cost`: sum of DPR machinery entries (amount) in date range
  - `labour_cost`: sum of expenses where category = labour in date range
  - `misc_cost`: sum of expenses where category = misc/other in date range
  - `total_cost`: sum of all cost categories
  - `net_profit`: production_value − total_cost
  - `profit_percent`: `null` when production_value = 0 or production_value < 0; otherwise `(net_profit / production_value) × 100`. **Never divide by zero.**
  - Response type for `profit_percent` is `Decimal | None` (nullable)
  - Include daily breakdown list: `[{ date, production_value, total_cost, net_profit, profit_percent: Decimal | None }]`

**Required UI change:**
- New section on `DashboardPage` or new `ProfitabilityPage`:
  - Date range picker (default: current month); also quick-select: This Week / This Month / Project to Date
  - Cards: Production Value | Total Cost | Net P&L | Margin %
  - `profit_percent = null` → display "—" (not "0%" and not an error message)
  - Negative `net_profit` → display as red number with a minus sign. Do NOT show a warning alert or error state. Negative P&L is expected during early project phases.
  - Breakdown bar: material / machinery / labour / misc costs as proportional segments
  - Daily table: one row per day in range; rows with `profit_percent = null` show "—" in that column
  - **Weekly and monthly aggregates are the primary view.** Daily P&L is highly volatile (one big BOQ measurement entry can swing a day from -100% to +40%). The date-range picker defaults to "This Month" to guide users toward the meaningful view.
  - Positive P&L → show in green; Negative P&L → show in red as a number, not as an alert/error

### GAP 11 — DPR entry for "no work" days (MINOR)

**Observed in Detailed measurements sheet:** Entries like "Sunday no work" (2023-09-24), "No work due to heavy rain" (2023-09-29, 2023-09-30). These are explicitly recorded to account for all calendar days.

**Important distinction from GAP 6a:** A "no work" day (GAP 11) is fundamentally different from a zero-production pre-work day (GAP 6a):
- **No work day:** No one came to site. Zero production AND zero expense. Reason is documented (rain, holiday, Sunday). The DPR is created as a formal record for the date even though nothing happened.
- **Pre-work/zero-production day (GAP 6a):** Contractor's team IS on site doing preparatory work (steel tying, formwork, dewatering, site clearing). Zero BOQ production can be claimed, but real expenditure (labour, machinery, material) is recorded. This is NOT a "no work" day. `no_work` must be false for these days.

**Current state:** DprHeader for a day either exists (work happened) or does not. There is no way to record "no work today" with a reason.

**Required backend change:**
- `dpr_headers`: add `no_work` BOOLEAN default false, `no_work_reason` VARCHAR(200) nullable
- If `no_work = true`: production entries are not required AND expenses should also be zero (a true shutdown day)
- If `no_work = false` and production entries are all zero: this is a valid pre-work day — do not treat it as "no work"
- Alembic migration required

**Required UI change:**
- DPR today page: "No work today" toggle with reason field (Rain / Holiday / Sunday / Other)
- When toggled, hide the production entry table and the expense entry sections, and show only the reason
- DPR calendar/history view: show "no work" days distinctly (greyed out with reason); show zero-production-with-expenses days differently (amber — work in progress, no BOQ qty yet)
- Tooltip or label on zero-production days: "Pre-work day — no BOQ quantity claimed"
